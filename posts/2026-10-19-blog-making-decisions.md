## 느낀 점

- **결과물이 나오는 속도보다 합의에 더 많은 에너지가 들었다**: 코드는 Claude Code가 빠르게 만들어냈지만, 정작 무엇을 어떤 형태로 만들지 방향을 정하고 합의하는 데 훨씬 많은 에너지가 들었다.
- **개발 루프와 판단 기준에 대한 경험 부족**: 개발의 전체 루프를 제대로 알아야 한다고 느꼈다. 각 단계마다 내가 무엇을 결정해야 하고 에이전트에게 어떤 역할을 맡겨야 하는지 지식과 경험이 부족했다. 다음 작업을 즉시 상세히 명세할 수 있다면 가장 좋겠지만, 최소한 지금 단계에서 무엇을 확인해야 하는지 알고 있어야 번복과 재작업을 줄일 수 있다.
- **서브에이전트의 관심사 분리와 오케스트레이션**: 서브에이전트는 단순히 토큰을 아끼는 수단이 아니라, 세션별로 관심사를 격리해 할루시네이션을 줄이는 방법이 될 수 있다고 생각한다. 다만 세션을 쪼갤수록 전체 맥락을 쥐고 흐름을 조율하는 상위 모델의 오케스트레이션이 반드시 전제되어야 한다.
- **제약 조건 하에서의 제어 역량**: 이번 프로젝트에서 전제 검증 실패, 모호한 지시, 권한 범위 설정으로 겪은 시행착오들이 결국 '에이전트의 컨텍스트를 어떻게 설계하고 통제할 것인가'의 문제였다고 생각한다. 제한된 조건 안에서 에이전트의 동작을 정확히 통제하는 경험을 더 쌓아야 한다.

## 무엇을 만들었나

Claude Code와 함께 이 블로그를 만들었다. 내가 방향을 정하고 판단했고, Claude Code가 코드를 작성했다.

완성된 결과물은 다음과 같다:

- **사이트**: Astro 정적 사이트, GitHub Pages 배포
- **디자인**: 상단 고정 배경 영역, 밝은 본문, 사이드 목차 (시안 Q4)
- **검색 및 탐색**: Pagefind 검색, 태그 모아보기 페이지
- **원고 검사**: TypeScript와 Python 양쪽에서 동작하는 검증 규칙
- **등록 도구**: tkinter GUI. 사전 검사 → 원고 검사 → 배치 → 빌드 확인 → 커밋 → push → Actions 대기 → 운영 확인의 8단계 파이프라인. 단계별 로그 기록과 실패 시 원상복구 포함

세 세션에 걸쳐 진행했고, 64건의 결정을 내렸다. 이 중 28건이 번복되거나 수정됐다.

## 주요 의사결정

### 1. 관심사 분리

저장소의 책임을 "작성이 완료된 마크다운 글을 정해진 디자인과 절차로 배포하는 것"으로 한정했다.

- 글 집필은 Git 추적에서 제외된 `desk/`(Obsidian vault)에서 한다.
- 등록 도구가 원고 형식을 검증한 뒤 `posts/`로 옮기면, 그때부터 저장소의 관리 범위에 들어온다.
- 이 경계를 정한 뒤로는 기능 추가 여부를 "이 작업이 저장소의 책임 범위에 속하는가"로 판단했다. 범위 밖이면 논의하지 않았다.

### 2. 시안 비교를 통한 디자인 확정

디자인을 말로 설명하지 않고, 시안을 단계별로 비교해서 골랐다.

1. **배경색 선정과 실패**: 4가지 배경색 시안(A~D) 중 아이보리(C)를 선택했으나, 본문 영역과 배경의 명도 차이가 부족해 구분이 안 되는 문제가 생겼다.
2. **참고 사례 확인**: 기술 블로그들이 사이드 메뉴나 목차로 시각적 대비를 만드는 구조를 쓰고 있었다.
3. **레이아웃 재조합**: 5가지 레이아웃 시안(P0~P4)을 요소별로 평가한 뒤 재조합해 Q1~Q4를 만들었다. 상단 고정 배경 영역과 사이드 목차로 본문을 분리하는 Q4를 채택했다.

### 3. 개발 원칙 키워드 적용

평소 바이브 코딩에서 쓰는 키워드 8개를 이 프로젝트에도 적용하도록 지시했다:

- 코드 재사용성 / 인터페이스 우선 설계 / 모듈 경계 명시 / TDD 먼저
- 완료 기준 선 정의 / AGENTS.md로 규칙 문서화 / 리뷰 가능한 크기 / 이해 가능성 유지

Claude Code가 이를 AGENTS.md의 개발 원칙 7개로 구체화했다. "코드 재사용성"은 모듈 경계와 이해 가능성이 확보되면 따라오는 결과이므로 별도 항목에서 뺐다. 모듈 경계는 모듈별 책임 표로 정리됐고, 완료 기준은 검증 루프의 첫 단계가 됐다.

### 4. 결정론적 등록 파이프라인

글 등록 절차를 8단계 파이프라인으로 고정했다. 같은 입력에 같은 결과가 나와야 하므로, 파이프라인 내부에 LLM을 개입시키지 않았다. 모든 단계는 로그를 남기고, 실패 시 원상복구한다.

### 5. 검증 루프

모든 작업에 앞서 Claude Code가 완료 기준 표를 먼저 작성하도록 했다. 기준이 없으면 작업을 시작하지 않는다. 작업 후에는 기준마다 검증을 실행하고 결과를 보고한다.

스크린샷은 디자인이 바뀔 때만 찍는다. 처음에는 매 글마다 찍게 했지만, 글 등록 시 디자인은 고정이므로 불필요하다고 판단해 뺐다.

이 루프는 처음부터 있던 것이 아니다. 내가 "검증 과정이 없다"고 지적한 뒤에야 규칙으로 추가됐다.

## 발생한 문제와 원인

28건의 번복 과정에서 드러난 주요 원인은 네 가지다.

### 1. 검증하지 않은 전제

- **저장소 분리 재작업**: 포트폴리오 저장소 안에 블로그를 두는 구조로 시작했는데, 그 전제에 근거가 없었다. 외부에서 가져온 정보로 팩트체크하는 과정에서 분리가 필요하다는 걸 알게 됐다. 계획서를 3번 다시 쓴 끝에 독립 저장소로 이전했다.
- **`_drafts` 구조 충돌**: Claude Code가 내 확인 없이 `_drafts` 구조를 만들었다. "글은 Obsidian에서 쓴다"는 의도와 맞지 않아 작업이 진행된 뒤에 걷어내고 `desk/` 구조로 교체했다.
- **실명 유입**: 다른 저장소의 상수를 복사하면서 실명이 코드에 들어왔다. 검증 도구에 해당 검사 항목이 없어서 배포된 사이트에서 내가 직접 발견했다.

### 2. 모호한 지시

- **CLI/GUI 혼선**: "rule-based로 문서 추가 도구를 만들라"고 지시하자 CLI가 나왔다. 내가 원한 건 GUI였다. 방향을 바꿔 tkinter 기반으로 다시 만들었다.
- **README 독자 미정의**: README를 4번 다시 썼다. 처음에 독자를 정하지 않아 6번 왕복한 뒤에야 "나 자신(Python 사용자)"으로 한정하고 구조가 잡혔다.
- **완료 기준 표 협상**: 완료 기준이 중요하다고 했으면서, 기준을 어떻게 도출할지 절차를 정하지 않아 표를 확정하는 데 3번 협상했다.

### 3. 진행 허가의 부작용

- **비교 데이터 삭제**: "단계별 승인 없이 끝까지 진행하라"고 위임하자 Claude Code가 샘플 포스트를 삭제했다. 나중에 디자인을 비교할 기준 데이터가 사라졌다.
- **로컬 전용 문서 공개**: 로컬에만 유지해야 할 문서가 포함된 커밋이 공개 저장소로 올라갔다. 여러 커밋이 쌓인 뒤에야 인지했다.

### 4. 검증의 한계

- **원상복구 범위 버그**: 등록 도구의 rollback에 버그가 있어, 현재 실행 이전에 수동 편집한 파일까지 되돌리는 문제가 있었다. pytest를 통과했지만 실제 원고로 리허설(등록 도구를 처음 실행하는 것)을 돌리면서 발견됐다.
- **검사 항목 부재**: 실명 노출은 검사 항목 자체가 없어서 발생했다. rollback 버그는 "실행해야 드러나는 결함"이고, 실명은 "검사 항목에 없었던 결함"으로 놓친 이유가 다르다. 문제가 발생한 뒤 규칙을 보강했고, 이후 같은 유형의 문제는 반복되지 않았다.

## 다음에 바꿀 것

이번 프로젝트에서 겪은 시행착오를 바탕으로, 다음 작업에서 개선할 4가지 목표다.

1. **개발 원칙 키워드 자동 적용**: 세션마다 8개 키워드를 수동으로 넣지 않고, 세션 시작 시 자동으로 읽히게 한다.
2. **개발 루프 절차 정의**: 지켜야 할 원칙만 나열하지 않고, 계획 → 구현 → 검증으로 이어지는 작업 순서를 정해 둔다.
3. **전제 검증 의무화**: 구현 전 계획 단계에서 모든 결정에 "결정 + 근거 + 출처"를 남기고, 확정된 것과 제안 중인 것을 구분한다.
4. **진행 허가와 비가역 동작의 분리**: 자율 진행 권한을 주더라도 파일 삭제, 원격 push, 외부 공개 같은 비가역 동작은 별도 확인을 거치게 한다.

## 도입하고 시도할 것

위 4가지를 해결하기 위해 다음 프로젝트에서 직접 적용해 볼 방법이다.

### 1. CLAUDE.md와 memory로 키워드 자동 주입

세션마다 반복하던 키워드 입력을 없앤다. 프로젝트 루트의 `CLAUDE.md`에 핵심 원칙을 적어 두면 Claude Code가 세션 시작 시 자동으로 읽는다. 프로젝트를 넘어 공통으로 적용할 원칙은 memory에 등록한다.

### 2. GitHub Spec Kit 적용 (명세 주도 개발)

모호한 요구사항과 근거 없는 전제로 인한 재작업을 줄이기 위해, GitHub의 오픈소스 도구인 Spec Kit을 적용해 본다. 코드를 작성하기 전에 Spec → Plan → Tasks → Implement 4단계를 거치는 구조다. 기획 단계에서 요구사항과 형태(CLI인지 GUI인지 등)를 마크다운 명세로 먼저 고정하고, 결정마다 확정/제안 상태를 구분해서 적는다.

### 3. 서브에이전트 분리 (`.claude/agents/`)

하나의 세션에서 기획과 구현이 뒤섞여 Claude Code가 합의 전에 코드를 만들기 시작하는 문제가 있었다. `.claude/agents/`에 기획 전용 에이전트를 만들고, 사용 가능한 도구를 읽기 전용(Read, Glob, Grep)으로 제한한다. 명세 합의가 끝난 뒤에만 구현 에이전트로 작업을 넘긴다.

### 4. PreToolUse Hook으로 비가역 동작 차단

"끝까지 진행하라"는 허가를 줘도 삭제나 push는 막아야 한다. `.claude/settings.json`에서 읽기·빌드·테스트는 자동 허용하되, 파일 삭제(`rm`)와 원격 push(`git push`)는 PreToolUse Hook을 걸어 차단(deny)한다. 일반 작업은 빠르게 진행하고, 비가역 동작 직전에만 승인을 요구하는 구조다.
